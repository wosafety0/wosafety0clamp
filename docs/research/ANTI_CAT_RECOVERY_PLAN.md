- **本文件性质：** 未来功能设计与实施路线，不代表已经实现或实机验证。

## 1. 目标与边界

防猫不是简单地定时刷新页面，也不是无限重试。目标是在游戏客户端出现错误画面、网络连接异常或数据长时间不更新时：

1. 尽早发现异常并停止新的游戏操作；
2. 保留异常前的操作与舰队状态证据；
3. 在有界等待和恢复尝试后重新建立 CDP/Poi 观察；
4. 重新读取并核对真实游戏状态；
5. 只有证据充分且不存在未决操作时才恢复调度；
6. 无法唯一确认状态时保持暂停，交由人工处理。

**最高原则：宁可暂停，也不重复派遣、不误结算、不对未知状态继续点击。**

本功能只管理客户端可观察到的运行异常和安全恢复，不尝试绕过游戏服务端限制、反作弊机制或网络地域限制，不修改系统代理/网络设置，不直接调用或重放游戏服务器 API。

## 2. 故障分类

检测器不得把所有异常都归为“猫”。至少区分：

| 类别 | 观测证据 | 初始处理 |
|---|---|---|
| 游戏猫画面 | 稳定视觉帧命中经校准的错误/猫画面模板 | 暂停游戏动作，记录视觉证据 |
| 游戏页面错误 | 已识别的错误页面、维护或会话失效提示 | 暂停；等待页面状态变化或人工处理 |
| 网络无响应 | 被动观察超时、自然响应长期缺失、连接关闭 | 暂停；有界等待自然网络恢复 |
| CDP 断连 | WebSocket/目标连接关闭、协议错误 | 暂停；重新建立只读观察连接 |
| Poi 数据陈旧 | 快照年龄超限、自然响应 witness 缺失或与 Redux 状态不匹配 | 暂停；重新取得新鲜 witness |
| 客户端进程异常 | Poi/Game WebView 不可用或目标消失 | 暂停；不自动重启外部进程 |
| 未知异常 | 视觉、网络和状态证据互相矛盾或无法分类 | 保持暂停，不猜测 |

视觉错误模板必须从当前实际客户端画面校准；本设计不假设已有可用的“猫”模板，也不把一次弱匹配当成确认。

## 4. 建议状态机

```text
RUNNING
  └─ 异常信号 → SUSPECT
       ├─ 证据不足/短暂抖动 → 有界复核
       └─ 异常确认 → PAUSED
            ├─ invalidate 当前 generation
            ├─ 禁止新的派遣、补给、结算点击
            └─ 保存异常快照与未决动作
                 ↓
             WAIT_NETWORK
                 ├─ 超时/反复失败 → MANUAL_REQUIRED
                 └─ 网络恢复信号
                      ↓
                 RECONNECT_OBSERVER
                      ├─ CDP/Poi 不可用 → 有界重试后人工处理
                      └─ 观察连接恢复
                           ↓
                      WAIT_FRESH_STATE
                           ├─ witness 陈旧/缺失/不匹配 → 继续等待或暂停
                           └─ 新鲜状态通过
                                ↓
                           RECONCILE
                                ├─ 有 UNKNOWN 动作或状态歧义 → MANUAL_REQUIRED
                                ├─ 仍有待结算结果 → 交给现有结算流程
                                └─ 舰队/任务/操作账本一致
                                     ↓
                                  RESUME_ALLOWED
                                     ↓
                                  RUNNING
```

状态转换必须单向、可审计。任何新一轮异常、超时、取消或进程关闭都应使旧 generation 失效；迟到的回调不得继续点击。

## 5. 恢复策略

### 5.1 第一层：只暂停，不做页面破坏性操作

异常确认后立即：
- 暂停 Supervisor 的新派遣与所有非必要 UI 动作；
- 使当前观察 generation 失效；
- 不重放点击、不重发游戏请求；
- 记录异常类别、首次/最近发生时间、页面状态、CDP 状态、最近自然响应时间、Poi 快照年龄及 Action Journal 未决条目。

### 5.2 第二层：有界等待与只读重连

- 优先等待被动 observer 捕获新的自然网络响应。
- CDP 连接断开时，只恢复观察连接，不立即刷新游戏页面。
- 使用有上限的指数退避或分段退避；设置最大等待时长、最大重连次数和熔断状态。
- 取消、超时和关闭时必须终止子进程/观察任务并释放监听器。
- 禁止通过轮询 MCP 或主动请求游戏 API 来制造“新鲜度”。

### 5.3 第三层：可见 UI 恢复（单独验收）

只有在只读重连无法恢复且已识别出明确、稳定、可恢复的页面状态后，才评估正常 UI 恢复动作。

- 每个动作前必须有新鲜状态门禁、明确目标和审计日志。
- 任何刷新/导航动作都必须有动作前后状态证据。
- 不允许在输入结果 UNKNOWN 时自动重复点击。
- 浏览器/WebView reload 不作为默认恢复方式；必须先评估是否会丢失游戏操作结果或造成重复提交，并通过独立测试和明确运行授权。
- 不自动重启 Poi、修改代理或改变系统网络配置。

### 5.4 第四层：恢复后状态对账

恢复运行前至少核验：
- 当前游戏页面稳定且可识别；
- 新鲜自然 port witness 已捕获，且与当前 Poi Redux 读取匹配；
- 每支受管理舰队的 mission tuple、舰船集合和状态均可解释；
- Action Journal 不存在无法判定的 submitted/unknown 操作；
- 派遣注册表/派遣事件与实际舰队状态不存在冲突；
- 已返航但未结算的任务进入现有 Witness/Settlement Drain，不得被当作空闲舰队；
- 补给、派遣和结算目标唯一，所有安全门禁通过。

任一项缺失、冲突或多重匹配，均进入 `MANUAL_REQUIRED`，不得自动恢复调度。

## 6. 分阶段实施路线

### 阶段 A：故障分类与只读检测
- 核对真实猫画面和常见错误页样本，建立模板/页面分类证据。
- 统一 observer 状态、CDP 错误、Poi freshness 和视觉状态的故障分类。
- 只发出诊断事件和暂停建议，不发送游戏 UI 输入。
- 离线测试覆盖误报、漏报、连续帧、弱匹配和冲突证据。

### 阶段 B：暂停与观察器恢复
- 把异常确认接入统一 Supervisor pause。
- 为恢复轮次引入 generation 隔离，复用现有 `ReturnRefreshCoordinator` 的失效语义或抽取最小通用能力。
- 实现 observer/CDP 的有界重连、取消和资源释放。
- 验证旧轮次回调零点击、暂停期间零派遣。

### 阶段 C：状态重建与安全续跑
- 复用 Action Journal、派遣记录、Witness 和 Settlement Drain 做恢复对账。
- 覆盖派遣点击前异常、点击后 UNKNOWN、派遣确认后断线、返航中断、结算中断、补给中断。
- 只允许唯一、可验证的状态进入 RESUME_ALLOWED。
- 任何无法对账的情况转人工处理。

### 阶段 D：可见 UI 恢复与实机验收
- 先做只读观察验收，再做单次、受控的可见 UI 恢复。
- 每一种恢复动作分别取得明确授权并限定点击范围。
- 不重复派遣来制造故障样本；优先使用离线故障注入和自然发生的异常。
- 完成单舰队后再验证多舰队；完成单次恢复后再做连续运行/长时间 soak test。

## 7. 必须覆盖的故障注入矩阵

| 注入点 | 预期结果 |
|---|---|
| 派遣前 CDP 断开 | 0 次点击、0 条成功派遣记录 |
| 派遣点击后、Poi 确认前断开 | 动作保持 UNKNOWN，不自动重试 |
| 派遣确认后网络断开 | 恢复后按派遣账本和 mission tuple 对账 |
| 返航计时到达但无新鲜 witness | 不判定返航，不触发结算 |
| 结算页面中途猫/断网 | 暂停 Drain，恢复后重新识别页面与结算阶段 |
| 补给点击后数据延迟 | 只读等待有界传播，不重复补给点击 |
| observer 子进程超时/取消 | 子进程退出，线程和监听器可释放 |
| 旧 generation 回调迟到 | 0 次 UI 点击 |
| 两舰队同时待结算 | 恢复后仍由全局 Drain 处理，归属唯一 |
| 多候选派遣归属 | `UNATTRIBUTED`，不猜测、不续跑 |
| 恢复后 Poi 与网络 witness 不匹配 | 保持暂停 |
| 连续猫/反复重连失败 | 熔断并转人工处理 |

## 8. 验收标准

1. 异常检测不会把普通页面转场、短暂延迟或单帧误匹配当成猫。
2. 确认异常后，所有危险 UI 动作立即停止。
3. 所有等待、重连、恢复动作均有次数和时间上限。
4. 取消和关闭能释放子进程、线程和事件监听器。
5. 旧 generation 永远不能发出新 UI 输入。
6. 恢复前必须取得新鲜自然响应 witness 并完成 Poi 状态对账。
7. UNKNOWN、重复候选、缺失数据和冲突状态全部 fail-closed。
8. 恢复逻辑不会重复派遣、重复结算或重复补给。
9. 日志可以重建从异常发生到恢复/人工接管的完整时间线。
10. 单舰队、多舰队和连续运行分别验收，不以离线测试代替实机验收。

## 9. 非目标与禁止事项

- 不以定时刷新代替异常检测。
- 不无限重试、不盲目重复点击。
- 不调用、重放或伪造游戏服务器 API 请求。
- 不绕过游戏限制或反作弊机制。
- 不擅自改代理、系统网络设置或 Poi 全局配置。
- 不自动重启外部进程或执行未经验证的浏览器 reload。
- 不新建第二套 Action Journal、派遣账本、网络观察器或运行日志。
- 不把一次恢复成功推断为无人值守长期运行可靠。
