- 审计对象：`correlation_scope()` / `dispatch_id` / 关联缺失可见性 / `action_id` 边界 / 结算与补给生命周期
- 基线：分支 `feat/production-settlement-resupply-wiring-20261105`，HEAD `bd9d189`
- 性质：**只读审计**。本轮不改任何生产代码、不改事件名、不改 schema、不改默认配置。
- 方法与证据：逐行读源码 + 在临时目录用离线脚本实测行为（`tempfile.mkdtemp`，未触碰 `logs/`、未启动 Poi/CDP、未点击、未派遣）。下文标注 `[实测]` 的结论来自脚本输出，其余为静态阅读。

## 1. `correlation_scope()` 的嵌套、异常退出与上下文恢复

### 结论：基本正确，可以放心嵌套；有两个非缺陷缺口

| 场景 | 结果 | 证据 |
| --- | --- | --- |
| 外层 `dispatch_id` + 内层 `action_id` | 内层继承 `dispatch_id`，只覆盖 `action_id`；退出后 `action_id` 回到 `None`，`dispatch_id` 仍在 | `[实测]` `outer/inner/after_inner` 三行：`dispatch-A/None` → `dispatch-A/action-1` → `dispatch-A/None` |
| 体内抛异常 | `finally` 复位 token，上下文完全还原，后续行不继承 | `[实测]` 退出后 `context=(None, None)`，`after_boom` 的 `dispatch_id=None` |
| 非法字段值（如 `fleet_id=0`） | 在 `ContextVar.set()` **之前**由 `CorrelationContext.with_()` 抛 `ValueError`，不留半套状态 | `[实测]` 抛出后外层 `dispatch-C` 仍在，`still_scoped` 行为 `dispatch-C` |
| `TeeEventSink` 子 sink 进入失败 | `ExitStack` 逆序回卷，已进入的子 sink 全部复位 | `[实测]` 第二个 sink `__enter__` 抛错，第一个 sink 退出后 `dispatch_id=None` |

机制上没有问题：`RunLogSink.correlation` 用 `token = set()` / `finally: reset(token)`（`sink.py:153-159`），`TeeEventSink.correlation` 用 `ExitStack`（`sink.py:370-378`），两者都是正确的成对语义。嵌套之所以能"继承而非清空"，是因为 `with_()` 只替换传入的槽位（`event_envelope.py:249-259`）。

### 缺口 1（中）：跨线程静默丢失，且方向是"丢"而不是"错"

`contextvars` 不随 `threading.Thread` 继承。`[实测]` 在作用域内启一个线程发射，该行 `dispatch_id=None, fleet_id=None`，主线程同一作用域内的行正常。

当前生产路径**恰好安全**：`background_port_snapshot_provider` / `port_response_observer` / `mission_result_observer` 三个后台线程都不持有 `event_sink`（`grep event_sink` 无命中），所有发事件的动作都在 `supervisor.tick()` 的同一线程内。但 `cdp_websocket` 已有 `cdp-event-reader` 线程，一旦将来把某个 CDP 回调直接接到 `event_sink`，这些行的 `dispatch_id` 会**静默变空**——方向是安全的（不会伪造归属），但阅读者无法区分"没有派遣"与"线程丢失"。

### 缺口 2（低）：`correlation_scope()` 不返回生效上下文

`RunLogSink.correlation` 的 `yield scoped` 会交出上下文，但 `TeeEventSink.correlation` 与 `correlation_scope()` 都 `yield None`（`sink.py:378, 400-403`）。后果是调用方**必须**在进入作用域之前把 id mint 出来并自己持有——这正是第 2 节"mint 失败无法记录"的直接成因。若让 `correlation_scope` 交出生效上下文（或接受 `dispatch_id_factory`），mint 就能被包进同一个 `try`。

## 2. `dispatch_id` 生成失败时的退化行为与告警

### 结论：**fail-closed 成立，但完全不可观测**（高）

`_dispatch_with_identity()` 的写法是 `with correlation_scope(self._sink(), dispatch_id=new_dispatch_id(), fleet_id=fleet_id)`（`continuous_supervisor.py:413-416`）。`new_dispatch_id()` 作为实参在 `correlation_scope` 之前求值，因此：

- `[实测]` 让 `new_dispatch_id` 抛 `RuntimeError`：异常从 `supervisor.tick()` 原样逃出，**控制器一次都没被调用**（`attempts == []`，没有发生派遣）。
- `[实测]` 此时运行日志里只有 `run_started` 一行，`degraded_reason is None`。**没有任何一行说明为什么这次派遣没有发生。**

也就是说：安全方向是对的（宁可不派遣），可追溯性为零。操作规程要求"安全停止必须记录停止条件与理由"，这里恰好漏掉。

### 关联缺口（高）：`_record_decision` 只在成功路径上

`tick()` = `_tick_once()` 后 `_record_decision(result)`（`continuous_supervisor.py:253-254`）。任何让 `_tick_once()` 抛异常的路径都拿不到 tick 汇总行：

- `[实测]` `monitor.tick()` 抛 `ContinuousMonitorError("state not trusted")` → **运行日志 0 行**。这恰恰是生产中最常见的停止（freshness 未验证时每轮都会发生，见 `one_expedition_ui_loop` 的 `--wait-for-return` 分支注释）。`supervisor_paused` 是 26 个关键审计事件之一，但它在异常路径上永远不会被发出。
- `[实测]` 双 READY 舰队、第二队在派遣中抛错 → 舰队 2 的 5 行派遣事件在盘上，**没有 `supervisor_tick` 汇总行**，第二队失败的原因（`boom`）不在日志里。

这不是 `dispatch_id` 的问题，而是"关键决策只在 happy path 记录"的结构问题；它比 id mint 失败更常发生，建议优先修。

### 缺口 3（中）：sink 根本装不下身份时仍然 mint

`[实测]` 把 `event_sink` 换成 `object()`（非可调用）：`new_dispatch_id()` 仍被调用 1 次，派遣照常发生（`attempts == [2]`）。

含义是**纯观测功能有能力阻断一次派遣，而阻断理由它自己无处记录**。这与 fail-closed 的初衷相反：fail-closed 应针对"审计行写不进去"，而不是"一个没人接收的 id 生成不出来"。最小修法：只在 `sink` 支持关联时才 mint。

## 3. Sink 不支持 correlation 时，缺失是否可识别

### 结论：**结构上不可识别**（中）

`correlation_scope` 在没有 `correlation` 属性时单纯 `yield`（`sink.py:398-401`），不记录任何东西。

`[实测]` 用一个普通函数当 sink（`hasattr(sink, "correlation") is False`）跑完整 tick：所有行的 `dispatch_id` 都是 `None`，**没有任何标记行**说明"本 run 不具备关联能力"。

于是阅读者面对的是同一个观测值 `dispatch_id: null`，对应至少四种完全不同的现实：

1. 这个 run 的 sink 不支持关联（降级但正常）；
2. 作用域被意外丢掉（回归 bug）；
3. 该事件本来就不属于任何派遣（`supervisor_tick` 等）；
4. 事件来自另一个线程（第 1 节缺口 1）。

仅凭日志无法区分——这直接违反"不能把推断当成已验证事实"的原则。目前唯一的判据在代码里（`hasattr`），不在日志里。

建议（最小改动）：在 `run_started` 里写一个能力位（如 `correlation_capable: bool`），一次性、全局、可判定；降级事实随 run 一起留在盘上，后续所有 `null` 都有了解释前提。

## 4. `_click` 是否适合作为 `action_id` 的唯一生成边界

### 结论：**形态合适，但现在还不够格独占**（高）

**支持的理由**（形态正确）：

- `_click` 的顺序是 `continuous_ui_click_attempted` → `input.click()` → `continuous_ui_click_sent`（失败则 `continuous_ui_click_ambiguous` 后 re-raise）（`continuous_expedition_ui.py:243-265`）。在 `attempted` 之前 mint `action_id`，即使 sink 写失败，也能得到"这一次输入被拒绝"的可辨识记录——这正是 `dispatch_id` 在门禁之前 mint 的同一种逻辑。
- 它带 `action` 与 `step`，正好是 id 之外的人类可读描述。
- 11 个调用点覆盖了派遣全链（`open_sortie` → `open_expedition_list` → `select_mission_*` → `confirm_mission` → `select_fleet_*` → `start_expedition`）、返航（`return_home_port*`）、补给（`open_supply_menu`）、结算推进（`advance_*`）。

**不够格的理由**（三个旁路，按严重度）：

1. **高** —— 补给的两处点击绕过了 `_click`，而且是**先点后记**：
   - `continuous_expedition_ui.py:759` 舰队 tab：`self._input.click(...)` → 之后 `continuous_ui_supply_tab_click_sent`；无 `attempted`，异常时无 `ambiguous`。
   - `continuous_expedition_ui.py:805` 补给按钮：同上。
   - 后果不只是"少了 action_id"：这两次输入**没有前置审计行**，所以 sink 坏了也不会拦住点击——P0.2 论证的"靠发射顺序 fail-closed"在这两处不成立。而补给正是 Fleet 4 闭环里风险最高的动作。
2. **中** —— 刷新导航有自己的一套：`visible_ui_refresh.py:195/245` 直接 `self._input.click(point)`，事件族是 `ui_refresh_click_attempted/sent/repeated`（+ 聚合的 `ui_refresh_audit`），顺序正确但与 `continuous_ui_*` 平行。若 `action_id` 只在 `_click` mint，刷新点击永远没有 id。
3. **低** —— `cdp_ui_driver.PoiCdpContinuousUiDriver` 的 `_game_input.click`（532/590/740）是第三个输入边界；目前只有 `tests/test_continuous_ui_driver.py` 引用，属潜在而非活跃风险。

**语义澄清**：`_click` 是"一次物理输入"，不是"一个业务动作"。一次补给 = 4 次 `_click`；派遣 = 6 次。且第 594 行 `step=attempt` 把 `step` 用成了重试序号，所以 `step` **不能**当身份。若把 `action_id` 定义在 `_click`，必须同时把语义写成"一次已派发的输入"，业务动作的归组交给 `dispatch_id` / 未来的 `correlation_id`。

**建议次序**：先把 759/805 收进 `_click`（顺带修好 fail-closed），再 mint `action_id`；刷新族单独给 id 或明确排除并在文档里写明"刷新点击不带 action_id"。反过来做（先 mint，后收拢）会得到"80% 输入有 id、恰好补给没有"的日志，比没有 id 更容易误读。

## 5. 结算与补给是否需要独立生命周期关联 ID

### 结论：**需要**，且边界已经存在（中）

**现状**：结算与补给的行只带 `fleet_id`，没有任何一次性的 pass 身份。事件序列本身是完整的（补给：`continuous_ui_resupply_started` → tab/button 定位与点击 → `continuous_ui_resupply_completed` → 控制器 `resupply_confirmed` / `already_complete` / `blocked`；结算：`startup_settlement_*` 7 个事件，或 `settlement_resumed_after_result_taken` / `settlement_closed_without_reward_screens` / `settlement_blocked`）。

**问题**：同舰队两次补给、同舰队两轮结算，只能靠时间戳排序区分。这正是交接文档 4.2 明确禁止的那种合并——"相同舰队、相同任务"不等于"同一次"。

**边界已存在，不需要新造**：四个控制器都在 `ui_arbiter.operation(...)` 里跑：

```
continuous_dispatch_controller.py:265   continuous-dispatch-fleet-{id}
continuous_resupply_controller.py:160   continuous-resupply-fleet-{id}
continuous_settlement_controller.py:161 continuous-settlement-fleet-{id}
continuous_settlement_controller.py:343 startup-settlement-fleet-{id}
```

这与 `_dispatch_with_identity()` 的形状完全一致：一次锁定操作 = 一次生命周期。在里面 mint 一个 id 并用 `correlation_scope` 包住，驱动层发出的所有 `_click` / 页面确认行自动继承，emitter 一行不用改。

**放哪个槽**：建议用**已有的 `correlation_id`**（`new_correlation_id()` 已存在且已导出，信封 12 字段不动），再加一个诊断字段 `lifecycle_kind: "settlement_pass" | "resupply_pass"` 区分两类 pass。备选是给信封加 `settlement_id` / `resupply_id` 两个真槽位——语义更干净，但要改 `ENVELOPE_FIELDS` 这个对外契约和所有读取方，与本轮"最小改动"的原则冲突，建议留到结算/补给各自长出多步状态机时再评估。

**可选挂 `dispatch_id`**：结算在语义上属于某次派遣的收尾，能从 action journal 唯一确定时应当挂上 `dispatch_id`；但按交接文档 3.1 的结论，**归属只能用于审计与恢复，绝不能成为 Drain 推进的前置条件**。拿不到就是 `null`，不得阻断。

**另一个具体缺口**：`settle_one_returned` 的 happy path 没有 `settlement_started` 行（只有 `resumed_after_result_taken` / `closed_without_reward_screens`）。一旦这一轮以 `settlement_blocked` 结束，日志里找不到这一轮的开始边界。生命周期 id 会顺带解决它，但仍建议补一条开始行。

## 7. 建议的修复顺序（若批准）

1. **`_record_decision` 覆盖异常路径**（第 2 节）：把 tick 汇总/暂停行放进 `try/finally`，让最常见的 freshness 拒绝也有记录。影响面最小、收益最大。
2. **`run_started` 记录 `correlation_capable`**（第 3 节）：一行字段，换来所有 `null` 的可解释性。
3. **补给两处点击收进 `_click`**（第 4 节）：同时修复 fail-closed 顺序与 action_id 覆盖。
4. **`action_id` 在 `_click` mint**（第 4 节）：在 3 之后做，语义写成"一次已派发输入"。
5. **`correlation_id` 作为结算/补给生命周期**（第 5 节）：四个 `ui_arbiter.operation` 边界各 mint 一次。
6. `correlation_scope` 交出上下文 / 只在支持关联时 mint（第 1、2 节）：纯清理，可最后做。
