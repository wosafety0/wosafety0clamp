# 通用 AI 开发 Harness：架构与项目接入规范

> 状态：提案；本文件所在 PR 合并前，不视为已采纳的仓库级规范。
> 日期：2026-10-28
> 当前原型来源：`wosafety0/wosafety0clamp` 的 PR #11、PR #12；两者均为 Open、未合并。

## 1. 目标

建设独立、可版本化、可复用于多个代码仓库的 AI 开发 Harness。Harness 为 AI 辅助开发提供可审计的规则加载、任务上下文、验证门禁、语义审查、证据校验与报告流程。

目标是降低项目接入成本，同时保持项目特有的业务规则、测试和权限边界由各项目自行控制。

## 2. 非目标与安全边界

- 不接管或自动执行项目业务操作；KancolleBot 的游戏操作仍受项目自身安全边界约束。
- 不把任何项目的业务逻辑、游戏协议或专属验收规则塞进通用核心。
- 不将密钥、安装令牌、私人规则正文或敏感上下文写入日志、审查报告、工件或提交。
- 不以“AI 返回 PASS”代替确定性测试、人工审查、权限检查或必要的真实环境验证。
- 不自动合并 PR；部署、发布、远程写入和其他外部状态变更必须由项目授权策略控制。
- 不把一次离线单元测试通过描述成真实模型端到端验证或完整语义合规证明。

## 3. 分层架构

### A. 规则与策略层（由组织/用户管理）

- 全局规则可位于独立的私有仓库。
- 消费方必须显式固定规则 commit，并校验预期 Git Blob SHA 或等效不可变摘要。
- 无凭据、无法读取、版本不匹配或摘要不匹配时，严格门禁必须失败关闭。
- 规则读取凭据应限定到所需仓库和最小只读权限；不在日志输出规则全文或令牌。

### B. 通用 Harness 核心（独立仓库）

建议逐步沉淀以下能力，按独立模块测试：

1. 规则解析与完整性校验；
2. 项目配置/schema 校验；
3. 变更范围与任务上下文归集；
4. 确定性静态检查和测试编排；
5. 可选的 OpenAI-compatible 语义审查客户端；
6. 严格输出 schema、变更文件/行号/证据引用校验；
7. 统一审查报告与退出状态；
8. 可复用的 GitHub Actions workflow / reusable workflow；
9. 离线单元测试、契约测试与接入示例。

语义审查的结果至少区分 `PASS`、`NEEDS_CHANGES`、`INCONCLUSIVE`。网络失败、模型不可用、响应格式错误、证据无法核验或必要配置缺失不得降级为通过。

### C. 项目适配层（留在各项目仓库）

每个项目维护自己的配置和验收入口，包括：

- 项目标识、项目说明和任务范围；
- 规则版本固定值；
- 变更范围/忽略范围；
- 项目测试与 lint/type-check 命令；
- 项目专属安全约束和禁止操作；
- 归档/进度文档的权威路径；
- 语义审查是否启用、允许的模型端点策略和预算；
- 项目特定的验收与人工批准要求。

Harness 核心不得猜测项目目录、默认运行高风险命令或覆盖项目权限政策。

## 4. 项目接入契约（初步）

建议每个项目提供 `.harness/project.yml`，初期先由 schema 校验，不应在未实现/未测试的情况下宣称它已被自动执行。

建议字段：

- `schema_version`：配置契约版本；
- `project_id`：稳定项目标识；
- `rules.repository`、`rules.commit`、`rules.blob_sha`：固定规则来源；
- `validation.commands`：明确列出的低风险验证命令；
- `review.enabled`、`review.model_env`：可选语义审查配置，不含密钥值；
- `safety.forbidden_actions`：项目禁止操作；
- `persistence.progress_path`：项目权威进度记录位置；
- `permissions`：明确的只读/写入/发布边界。

未被当前 Harness 版本识别的必需字段、无效 schema 或不安全的默认值必须阻止门禁通过。具体字段类型与 schema 版本需在核心实现阶段通过测试固定。

## 5. 版本与分发

- Harness 核心使用语义化版本；未达到稳定契约前使用 `0.x`。
- 项目消费方固定到发布 tag 对应的 commit SHA，不默认追随浮动分支或 `latest`。
- 可复用 workflow 使用受保护的 tag 或完整 commit SHA 引用。
- 变更接入契约、审查输出 schema 或门禁语义时，应升级版本并提供迁移说明。
- 先在 Harness 仓库完成测试与发布，再通过独立 PR 更新消费项目；不得在多个项目里手工复制后任其分叉。
- Harness 不能替代项目自己的 CI；项目必须继续运行其专属测试。

## 6. 凭据、数据与失败策略

- 密钥仅通过 GitHub Actions Secrets / 环境变量注入；仓库文件和配置只存变量名，不存密钥值。
- 规则读取 token 采用短期、最小权限和最窄仓库范围。
- 发送给模型的 diff、规则和上下文应按项目策略最小化；私有代码发往外部模型前必须有明确的项目授权/提供方策略。
- 默认不把完整 diff、规则全文或模型原始响应打印到 CI 日志。
- 网络错误、超时、空响应、非法 JSON、schema 不匹配、证据引用不成立、缺少必要凭据均返回非通过状态。
- 报告必须区分“未执行”“执行失败”“通过”和“结果不确定”，不得把未执行描述为通过。

## 7. 实施顺序

1. 完成并审查本架构规范。
2. 在当前 KancolleBot 候选实现中确认语义审查器的接口、失败策略和离线测试覆盖。
3. 建立独立 Harness 仓库，先迁移规范、契约测试和最小核心，不迁移项目业务代码。
4. 在新仓库运行独立 CI，确认不依赖 KancolleBot 的目录或测试数据。
5. 在 Harness 仓库发布第一个固定版本（可为 `0.1.0`，仅在验收完成后）。
6. 让 KancolleBot 通过固定版本接入，保留项目适配文件和专属测试。
7. 在第二个独立项目试接入，记录所需配置、接入步骤、失败场景与修订。
8. 满足验收标准后再宣布可复用 MVP。

## 8. 验收标准

### 通用核心

- [ ] 可在与 KancolleBot 无关的干净仓库中安装/调用。
- [ ] 配置契约有 schema 与正反例测试。
- [ ] 无需模型 API 即可运行全部确定性离线测试。
- [ ] 模型/API 失败、响应非法、证据不符时均不能 PASS。
- [ ] 审查报告可追溯到输入 commit、规则固定版本、工具版本和验证结果，但不泄露密钥/敏感正文。
- [ ] 有固定版本或 SHA 的消费方式及升级说明。

### 规则与权限

- [ ] 全局规则固定 commit 与 Blob SHA 均校验。
- [ ] 缺失凭据、访问拒绝、版本漂移和摘要不匹配均 fail closed。
- [ ] 不具备自动合并或未授权发布能力。
- [ ] 项目适配层可声明自己的禁止操作、测试命令和归档路径。

### 项目接入

- [ ] KancolleBot 接入 PR 的 CI 全绿，并明确区分远程修改与本地同步状态。
- [ ] 第二项目按文档完成接入，未复制通用核心代码。
- [ ] 至少一组失败注入测试证明门禁不会把不确定状态误判为通过。
- [ ] 所有“通过”结论均有实际 CI/测试链接或可回读的提交证据。
